# Архитектура и структура репозитория

## Принцип

Строим модульный монолит. Учетное ядро отвечает за факты, расчеты и качество; сценарии приложения координируют загрузку и запросы; адаптеры работают с брокерами, курсами и PostgreSQL; Telegram только отображает результат. Направление зависимостей: внешние адаптеры зависят от контрактов ядра, а не наоборот. Второй сервис или отдельные пакеты не нужны до появления измеримой потребности.

ООП требуется для устойчивых границ (источник данных, хранилище, сценарий), но чистые функции для оценок и финансовых формул предпочтительнее искусственных классов. Интеграция с БД разделяется на инфраструктурный код подключения/миграций и прикладные репозитории. Брокерские клиенты не импортируют PostgreSQL и Telegram.

## Текущее состояние

Исполняемый код находится в `src/portfolio_v2`: `domain.py` содержит модели и расчеты, `service.py` координирует refresh/запросы, `adapters.py` объединяет T-Invest и Freedom, `fx.py` получает курс ЦБ, `storage.py` хранит PostgreSQL и выполняет DDL при старте, `bot.py` предоставляет Telegram. `run_portfolio_v2.py` собирает зависимости из переменных окружения. Тесты - в `tests/`. Это рабочий технический срез, не окончательная модульная граница.

## Целевая организация

```text
invest_cons/
  AGENTS.md
  README.md
  pyproject.toml                 # после оформления пакета
  .env.example
  compose.yaml
  config/                       # версии политик и схемы проверки
  migrations/                   # версионированный DDL, без импорта данных
  src/invest_cons/
    domain/                     # счета, позиции, деньги, события, оценки
    application/                # refresh, портфель, доходность, доходы
    integrations/
      brokers/                  # клиенты/адаптеры T-Invest и Freedom
      fx/                       # источники исторических курсов
      postgres/                 # подключение и реализации репозиториев
      telegram/                 # команды и форматирование
    bootstrap.py                # составление зависимостей и проверка конфига
    cli.py
  tests/
    unit/
    contract/
    integration/
  docs/
    adr/
  scripts/                      # только короткие эксплуатационные обертки
```

Каталоги `src/invest_cons`, миграций и разбивка тестов - целевое состояние. Перенос кода не выполняется созданием пустых папок: каждый перенос идет отдельным изменением с сохранением поведения, тестами и проверкой команд запуска. До этого `src/portfolio_v2` остается единственной исполняемой реализацией.

## Контракты и поток данных

```text
T-Invest / Freedom -> адаптеры -> исходные события и позиции -> PostgreSQL
                                           |                    |
                                           v                    v
                                    учетное ядро <-------- исторические данные
                                           |
                                  сценарии и DTO результата
                                           |
                                      Telegram / CLI

ЦБ и другие источники FX -> датированные курсы -> учетное ядро
```

Границы: брокерские форматы завершаются в адаптерах; расчеты не знают об SDK; SQL не вызывается из Telegram; на сохраненный снимок можно сослаться по ID, времени, охвату и версии метода. Классификация и инвестиционная политика позднее подключатся отдельным модулем, не изменяя фактические события.

## Конфигурация и развертывание

Секреты, DSN и параметры окружения приходят из переменных окружения или секретного хранилища. Изменяемые бизнес-правила находятся в версионируемом конфиге с проверкой схемы при запуске; версия политики прикрепляется к результату. Значения протокола и бухгалтерские инварианты не превращаются в настройки. Локальный и облачный PostgreSQL отличаются адресом подключения, не ветками кода.

DDL переносится из запуска в версионированные миграции. Миграция меняет только схему, импорт данных - отдельная идемпотентная команда. Перед облачным запуском нужны backup/restore, межпроцессная защита синхронизации и отдельный фоновый регламент.

Значимые решения и изменения границ фиксируются в [ADR](adr/README.md); первое решение - [модульный монолит](adr/0001-modular-monolith.md). Детальные учетные правила - в [контрактах данных](data_contracts.md).
