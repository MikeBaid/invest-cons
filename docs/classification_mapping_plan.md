Активные записи хранятся в `portfolio_v2.classification_history` с историей supersession и уникальностью одной активной записи на `(contour, instrument_id)`. Полная модель инструмента/алиасов и назначения на конкретный snapshot остаются будущим расширением.

Команда `python -m scripts.preview_portfolio_classification` остаётся read-only сверкой старого маппинга и snapshot. Состав счетов `personal_main` исключает две инвесткопилки и два счёта «под ключ», но включает «Портфельное инвестирование» и цифровой счёт.

## Что хранить

IPS хранит определения направлений и целевые веса. Фактическая привязка хранится в PostgreSQL отдельно:

- `classification_history` (реализовано) - активный лист по `(contour, instrument_id)`, версия правил, источник, основание и `valid_from/valid_to`. Частичный уникальный индекс запрещает две активные записи для одной пары.
- `instrument`, канонические алиасы брокеров, признаки и назначение бакета на конкретную позицию/snapshot - целевое расширение для полной истории инструмента и корректной обработки смены фактов.
- Старый JSON остаётся исходным материалом импорта; он не читается ботом при каждом отчёте и не является активной классификацией.

Для обычной позиции сумма назначенных долей равна 1.00. Для подтвержденного разложения фонда сумма долей по направлениям также равна 1.00. `unclassified` и вручную подтвержденный `other` различаются. Доля неопределенного NAV выводится отдельно и не исчезает из знаменателя портфеля.

## Что показала проверка старого файла

В нем 97 записей; у всех `source=xai_llm`, у 10 нет `instrument_uid`, а 23 имеют бакет `non-tradeable`. По последнему сохраненному снимку нового проекта после исключения инвесткопилок и счетов «под ключ» нашлись совпадения для 73 уникальных инструментов T-Invest по UID и 8 инструментов Freedom по ключу. Это покрытие **полученных** позиций: цифровой счет входит в `personal_main`, но его позиции в снимке недоступны. Совпадение идентификатора подтверждает связь записей, но не правильность старой классификации.

Пользователь подтвердил, что 7 USD-выпусков Freedom относятся к `external.bonds.kz_usd` с классом надежности B; выпуск `FFSPC4.0527.AIX.KZ` (EUR) остается на уровне `external.bonds`, без USD-листа. Российский старый бакет `currency_corp_bonds.replacement_bonds_usd` пользователь определил как класс A и сопоставил с `rf.bonds.usd_linked.aaa_aa_plus`. Рублевый `rating_AA_plus` дает класс A, но для целевого листа нужна детализация купона и рейтинга. `rating_A_to_AA` дает класс B, для него в текущем IPS нет листа. `non-tradeable` исключаются из инвестиционного контура.

## Одноразовый импорт

1. Сделать read-only копию старого JSON с хешем и версией исходного IPS. Импорт не должен обращаться к старой БД и не изменяет ее.
2. Сопоставить T-Invest записи по UID; при отсутствии UID использовать подтвержденную таблицу FIGI/UID. Freedom сопоставлять по идентификатору брокера, затем подтверждать экономический инструмент по документам выпуска. Не объединять разные бумаги по одному тикеру.
3. Записать все строки в `legacy_mapping_import`, включая сомнительные и неиспользуемые; импорт повторяем по хешу источника и ключу строки.
4. Сформировать предложения по новым признакам и направлениям; проверить валютную привязку, страну эмитента, тип купона, тип счета и ручную кредитную категорию.
5. Подтвердить или отклонить предложения. Только подтвержденные решения могут участвовать в `position_bucket_assignment` для новой версии IPS.
6. Сверить количество и стоимость назначенных, `other` и `unclassified` позиций по каждому счету и всего `personal_main`.

Старый файл остается материалом для инициализации, а PostgreSQL - источником активных и исторических решений. Политика и классификация версионируются независимо.
