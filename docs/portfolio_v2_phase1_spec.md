# Портфель V2: первый релиз

Статус: спецификация первого релиза, 2026-10-03. Изолированная реализация находится в `src/portfolio_v2` и пока не заменяет работающего бота. Первый технический срез включает оба брокера, сохранение снимков/операций, оценку в RUB/USD, результат по двум снимкам и доступные календари выплат. Ограничения и запуск описаны в `portfolio_v2_runbook.md`.

## 1. Граница релиза

Включены T-Invest и Freedom, все настроенные счета и владельцы. Результаты доступны по каждому счету, брокеру, владельцу и для выбранной совокупности счетов. Счета разных владельцев можно показывать вместе, но налоговые и денежные потоки не смешиваются между владельцами.

В релизе нет поиска активов, торговых рекомендаций, исполнения заявок и расчета будущих налоговых льгот. При этом сведения о владельце, брокере, типе счета и исходных операциях сохраняются с первой версии. Новая классификация может быть незаполненной: это не препятствует учету позиции или выплат.

## 2. Telegram: минимум команд

| Команда | Результат |
|---|---|
| `/start` | Доступные команды и дата последнего полного среза |
| `/refresh` | Запустить синхронизацию счетов, операций, FX и календарей; вернуть статус с отдельным результатом для каждого брокера |
| `/portfolio` | NAV в RUB/USD и интерактивное дерево: верхний уровень IPS → дочерние классы/листья → позиции → карточка позиции. Каждый экран показывает срез, RUB/USD и долю; целевая доля/сумма и отклонение берутся из версии IPS. |
| `/performance` | Период, старт/конец, внешние потоки, абсолютный результат, XIRR и TWR/оценка метода в RUB/USD; неполные метрики не выдаются числом |
| `/income` | Факт купонов/дивидендов и будущие события; раздельно подтвержденные и оценочные, с валютой и статусом |

Дерево и callback-навигация используют один snapshot на протяжении просмотра. Списки позиций постраничные; кнопки устаревшей сессии предлагают открыть `/portfolio` заново. При неполном срезе показываются наблюдаемые суммы узлов, но не доли портфеля и не денежные цели. IPS со статусом `draft` показывается как черновой ориентир, не как рекомендация. Никакой расчет не зависит от способа отображения в Telegram. Отчет показывает `as_of`, охват счетов и причину отсутствия числа. Доступ определяется стабильным Telegram user ID, привязанным к разрешенным владельцам.

## 3. Данные и источники

| Данные | T-Invest | Freedom | Правило полноты |
|---|---|---|---|
| Счета и текущие позиции | GetAccounts, GetPortfolio, GetPositions | Tradernet account_summary | Каждый ожидаемый счет отмечен `complete` или `failed`; пропущенный счет не превращается в пустой |
| Денежные остатки | GetPositions.money | account_summary.ps.acc | Остаток в исходной валюте, отдельно от стоимости бумаг |
| Операции | GetOperationsByCursor, вся доступная история + инкремент | getBrokerReport и при необходимости история сделок | Сохранить raw, статус и границу успешно прочитанного периода по счету; типы Freedom подтвердить образцами брокерского отчета |
| Курсы | Исторические курсы с датой и источником | Общий FX сервис | Требуются курсы на даты снимков и потоков; при отсутствии конвертации результат nullable |
| Купоны: факт | Операции | Брокерский отчет | Записи с ID/источником; выплаты тела долга отдельно |
| Дивиденды: факт | Операции | Брокерский отчет, после подтверждения типа событий | Неподтвержденное покрытие показывать как `unknown`, а не как ноль |
| Купоны: план | GetBondCoupons | Карточка инструмента / corporate actions | Отдельно будущая дата, сумма на бумагу, количество и надежность оценки |
| Дивиденды: план | GetDividends | Доступный календарь / corporate actions | Только объявленные события как подтвержденные; неизвестную дату не заменять датой реестра |

Текущий код Freedom достоверно использует `account_summary` для позиций, `cash_in_outs` для купонов и `getStockData` для купонного прогноза. Полнота дивидендов, вводов/выводов и истории сделок в его существующем парсере не подтверждена. Новый адаптер должен сначала сохранить и описать фактический ответ брокерского отчета (без секретов), после чего включить соответствующие категории в финансовый результат. Пока поле не подтверждено, общий результат с участием такого счета имеет статус `incomplete`.

## 4. Учетная модель

`Broker(id, contour)`: T-Invest = РФ, Freedom = внешний контур. `Owner(id)` хранит налогового владельца. `Account(id, broker_id, owner_id, account_kind, opened_at)` описывает счет и режим ИИС; налоги пока не рассчитываются.

`Instrument(id, broker_ids, type, issuer, currencies, terms)` не содержит налогового режима. `Holding(account_id, instrument_id, quantity_units, blocked_units)` относится к счету. У одного инструмента могут быть позиции на разных счетах.

`RawBrokerEvent(broker, account_id, external_id, revision, occurred_at, observed_at, payload)` и `NormalizedEvent` хранят факты. Нормализация версионируется. Внешние вводы/выводы классифицируются относительно выбранного контура портфеля; перевод между его счетами не создает прибыль.

`Valuation(account_id, instrument_id, as_of, quantity_units, price_native, price_currency, accrued_interest_native, native_value, fx_rates, rub_value, usd_value, quality)` хранит компоненты оценки. Цена на одну бумагу умножается на число бумаг. Для облигации правило включения НКД подтверждается сверкой с брокером. Недостающий FX не заменяется нулем.

`Snapshot(as_of, account_coverage, valuation_coverage, operation_coverage, method_version, nav_rub, nav_usd)` является неизменяемым результатом. Старые ошибочные снимки сохраняются как исторические записи старой методологии и не смешиваются в одной серии с исправленными.

`IncomeEvent` сохраняет факт и дату платежа, сумму/валюту и инструмент. `ForecastEvent` сохраняет тип источника, дату выплаты, дату фиксации права, сумму на бумагу, примененное количество, вероятность/статус и версию прогноза. Факт и план сопоставляются по счету, инструменту, типу и периоду.

Все деньги в ядре представлены Decimal. Текущие и исторические FX явно датированы. RUB и USD представляют две оценки одного исходного набора позиций и операций, а не две независимые книги. Любые дополнительные исходные валюты сохраняются без потери.

## 5. Финансовый результат

```text
net_external_flow_ccy = deposits_ccy - withdrawals_ccy
investment_pnl_ccy = end_nav_ccy - start_nav_ccy - net_external_flow_ccy
```

Формула применяется независимо в RUB и USD. Потоки конвертируются по курсам дат операций. Внутренние переводы, покупки, продажи, купоны и дивиденды, оставшиеся внутри портфеля, не прибавляются к внешним потокам.

XIRR рассчитывается по датированным внешним потокам, начальному отрицательному и конечному положительному NAV. Если период короткий, результата нет или он неоднозначен, отчет это показывает. В текущем техническом срезе TWR не рассчитывается: при двух снимках доступен явно подписанный Modified Dietz. Настоящий TWR требует отдельных срезов на границах внешних потоков.

Нельзя показывать численную доходность для группы, если хотя бы один включенный счет за период не имеет подтвержденного NAV или потоков. Можно показать меньшую, явно указанную группу счетов, где данные полны. Показатель «поступления / текущий NAV» не называть доходностью капитала.

Период YTD начинается 1 января только при наличии подходящего начального среза. Если он отсутствует, выбрать `с начала доступной истории` с фактической датой. Историческая серия нового ядра начинается с первого проверенного снимка, если брокер не предоставляет достаточный архив для восстановления более раннего NAV.

## 6. Синхронизация

Целевой фоновый регламент: полный EOD снимок всех счетов ежедневно; операции по счетам инкрементально и с overlap; календарь выплат ежедневно; FX для каждого нового дня и отсутствующих дат. Текущий технический срез предоставляет `/refresh` и CLI `--refresh-once`; расписание следует задать внешним планировщиком. Внутри одного процесса `/refresh` защищён lock, межпроцессная блокировка пока не реализована.

Для каждого счета отдельно фиксируются `attempted_to`, `success_to`, ошибки и охват. `success_to` продвигается только после полной загрузки и успешной записи всех страниц. Повтор безопасен благодаря idempotent ключу операции. Результат каждой синхронизации и недостающие данные видны пользователю и в технических логах.

## 7. Техническая граница

```text
broker adapters (T-Invest, Freedom) -> raw events / current holdings
                                   -> accounting core -> PostgreSQL
                                   -> performance / income queries
                                   -> Telegram presentation
```

Новый код не использует существующие расчеты `PositionView.current_value`, старый FX fallback или прежний `return_report` как источник финансовой истины. Низкоуровневые API вызовы и исторические raw данные могут служить материалом для новых адаптеров. Существующая БД доступна только для read-only импорта с lineage и проверкой качества. Новый процесс не запускается одновременно со старым ботом на одном Telegram token.

Минимальные тесты ядра: лот 10 / 100 акций, dirty value облигации, пропущенный FX, сбой одного счета, повтор операции, перевод между своими счетами, поток в начале и конце интервала, купон/дивиденд после продажи бумаги, объявленный против оценочного платежа. Адаптеры тестируются на обезличенных образцах ответов обоих брокеров.

## 8. Критерий готовности

Первый релиз принимается, когда пять команд работают на обоих брокерах, каждая позиция и валюта видна в своем счете, агрегированный NAV сверяется с брокерскими данными по согласованному правилу, неполный источник блокирует численные сводные доходности, а факт выплат совпадает с историей брокера на проверенном интервале. Для будущих платежей явно указан статус и происхождение каждой суммы. После перезапуска бота история и результаты не пропадают. Эти проверки на живом портфеле еще не завершены.
